## 스킬이 뭐임?

![책을 진지하게 들여다보는 페페 밈](../../assets/study/claude-skills-intro/01-what-is-skill.png)

스킬이란 재사용 가능한 작업 매뉴얼이라고 생각하시면 됩니다. 클로드가 특정 종류의 작업(엑셀 표 출력, PDF 다루기, 계약서 검토 등)을 할 때 매번 처음부터 방법을 알아내는 대신, 미리 만들어온 지침서를 불러와서 그대로 따라가게 하는 구조이죠.

필요한 것은 언제 쓸지를 다루는 트리거 조건과 어떻게 할지를 다루는 본문으로 구성되어 있습니다.

## 구조

```text
skill-name/
├── SKILL.md (필수)
│   ├── YAML frontmatter (name, description)
│   └── 마크다운 본문 (지침)
└── 부가 리소스 (선택)
    ├── scripts/    - 반복 작업용 실행 코드
    ├── references/ - 필요할 때만 불러오는 참고 문서
    └── assets/     - 결과물에 쓰이는 템플릿, 아이콘 등
```

클로드 코드의 아이디어는 필요한 만큼만, 필요한 시점에 클로드의 컨텍스트에 저장한다는 것입니다. 이러한 아이디어를 점진적 로딩이라 하며 3단계로 구성되어 있죠.

### 1단계 (메타데이터 / 항상 불러온 상태)

name + description. 대략 100단어 정도로 구성되어 있고, 사용할 수 있는 스킬이 몇십 개든 이 내용은 항상 클로드의 컨텍스트에 저장되어 있습니다. name은 스킬의 이름이고, description에는 클로드가 이 스킬을 써야 하는지 판단하는 근거가 되어 줍니다.

그래서 클로드가 이 요청에 어떤 스킬이 맞는지 훑어볼 때 이 목록이 사용됩니다. 가볍기 때문에 토큰도 얼마 안 든다는 거.

### 2단계 (SKILL.md 본문 / 호출될 때만 불러옴)

사용자 요청이 특정 스킬의 description과 일치한다면 이 본문 내용이 통째로 컨텍스트에 들어오게 됩니다. 실제 작업 지침, 절차, 예시가 다 들어 있고 500줄 이내로 유지하는 게 권장됩니다.

### 3단계 (부가 리소스 / 진짜 필요할 때만)

scripts/, references/ 들처럼, 본문이 "이러한 상황이면 references/aws.md를 읽어보라"고 가리켜줘야 읽어보는 내용들입니다. 크기 제한이 사실상 없습니다. 왜냐하면 전부를 한 번에 읽는 게 아니라 필요할 때만 읽기 때문이죠.

## 어떻게 만들어지나요?

![침침한 눈으로 더욱 몰입하는 짤](../../assets/study/claude-skills-intro/02-how-made.png)

1. 사용자 인터뷰: 뭘 하고 싶은지, 언제 호출되어야 하는지, 출력 형식이 무엇인지, 테스트 케이스가 필요한지 점검합니다.
2. SKILL.md 초안 작성: 설명(description)을 명시적으로 작성해 주어야 합니다. 클로드가 스킬을 자주 안 불러오려는 나쁜 습관이 있어서, 이런 이야기 나오면 무조건 이 스킬 써야 해!! 라고 해줘야 알아먹습니다.
3. 테스트: 테스트 프롬프트 2~3개 만들어서 스킬 있을 때와 없을 때를 비교하고 평가합니다.
4. 수정: 피드백 기반으로 스킬을 수정합니다. 왜인지 설명해야 클로드가 스스로 판단해서 유연하게 작성합니다.
5. 반복: 개선될 때까지 무한 반복합니다.
6. 최적화: 말했을 때 호출이 잘 되는지 20개 정도의 실제 유저 프롬프트 스타일 멘트를 테스트하고, 자동으로 문구를 다듬게 합니다.

그래서 제가 만든 프로젝트 관리 템플릿의 가이드 문서를 읽고, 이를 바탕으로 업무 생성·처리·기록을 맡아주는 스킬을 작성하고 싶어져 만들어 보았습니다.

## 노션 로그 스킬을 만든 동기

아 솔직히 팀플 그냥 해도 박살나고 힘들어 죽겠는데, 가이드 문서까지 읽고 규격대로 작성하고 해라 하면 죽어도 안 할 것 같아서, 아 이거 좋은 방법이 없나 고민을 했습니다.

![무한도전 "팀을 어떻게 짜신 거예요? / 아침부터 스트레스" 짤](../../assets/study/claude-skills-intro/03-motivation.png)

그때 떠오른 게, 그냥 클로드를 구매시키게 하고 해당 팀원이 한 대화 내용을 가지고 와서 실시간으로 업무하는 걸 알 수 있게 할 수 있을 것 같았습니다. 이를 클로드 스킬을 바탕으로, 귀찮은 업무를 대신 관리해주는 직원을 만드는 스킬을 만들면 되지 않을까 라는 아이디어를 바탕으로 해당 스킬을 구현하였습니다.

## 하 어케 만들지 (기획 단계)

일단 뭔가 시키고 싶은 건 많은데 뇌가 정리가 안 되어서, 필요한 기능에 대해 나열해 보았습니다.

![이것저것 해야 할 게 많아 고통받는 짤](../../assets/study/claude-skills-intro/04-planning.png)

- 노션의 가이드 문서를 읽고 가이드대로 업무를 수행하는 것
- 하나의 템플릿을 만들어놓고 여러 팀 프로젝트에 적용할 예정이므로, DB가 바뀔 수 있다는 점을 염려해야 한다는 것
- 필수적으로 받아야 하는 정보를 꼭 받아야 한다는 점
- 해당 대화 중에서 진행 사항을 변경해야 한다면 변경하고, 문제가 발생한다면 기록을 남기도록 설계
- 이후 프로젝트 과정에서 내 의견과 과정을 남기기 위해, 개인의 생각을 남길 수 있어야 한다는 점
- 결과·인사이트처럼 사용자 답변이 중요한 경우, AI가 대신 작성하는 게 아니라 사용자가 작성해야 한다는 점
- 산출물이 있다면 목표에 맞는 공유 자료실 폴더에 작성되도록 설정
- 주마다 스킬이 레포와 다르다면 업데이트하기
- 개인별 폴더에 맞는 기록 및 로그 남기기

와 이렇게 보니까 정말 할 거 많네요 미치겠냐.

## 구현 과정 요약

- 위에서 설명한 요구사항을 정의하였습니다. 노션의 템플릿 구조를 파악(업무 DB, 업무 로그 DB, 자료실 폴더)하고, 핵심 원칙을 합의했습니다 (ID 하드코딩 금지, 의견 창작 금지, 필수 요소 강제 등).
- 1차 SKILL.md 작성: 4개의 워크플로우(등록, 업데이트, 완료, 신규 프로젝트)와 판단 원칙을 정리하였습니다.
- 실전 테스트를 진행해 보았습니다. 진행 예정인 LG Aimers 노션 워크스페이스에서 업무 등록 → 보류 → 재개 → 완료까지 풀 사이클을 실행하였고, 세부 규칙이 공유 폴더에 나타나게 표현되는 것까지 확인했습니다.
- 뭔가 공식 문서엔 좋은 조언이나 방법이 있지 않을까 찾아보았더니, 가이드 문서를 읽고 반영하여 토큰 낭비 요소(매 액션마다 프로젝트 가이드를 반복 fetch 하던 걸, 프로젝트당·대화당 한 번씩만 읽고 재사용하게)를 수정하였습니다.
- GitHub 자가 점검 기능 추가: 원래는 예약 작업으로 설계하였으나, 모든 사용자에게 강제하긴 뭔가 그래서 스킬 내장 워크플로우로 설계하여 다르면 자동 업데이트를 하도록 했습니다.

## 결과

위 구현 과정을 통해 notion-project-logger라는 스킬을 제작하였습니다! 프로젝트 관리 템플릿이라는 노션 템플릿을 읽고, 클로드가 그 프로젝트 안에서 팀원처럼 행동하도록 만들었습니다. 구체적으로:

- 새 업무를 등록할 때 필수 필드(이름/진행상황/날짜)를 챙기고, 애매한 이름은 동사형으로 다듬게 유도
- 대화 중 "막혔어", "완료했어" 같은 신호를 감지해서 진행상황을 알아서 바꿈
- 업무 완료 시 결과·인사이트를 반드시 사용자한테 직접 받아서 기록(대신 창작 안 함), 산출물을 공유 폴더에 올바르게 배치
- 새 팀 프로젝트 시작할 때 개인 폴더 세팅 + 초기 업무 등록
- (오늘 추가한 것) 자기 자신의 GitHub 소스와 비교해서 주기적으로 자가 점검

## 자세한 기능들

### 1. 업무 등록

그냥 시키는 대로 바로 노션에 페이지를 만들면 안 되게 설정했습니다. 이름/진행상황/날짜 이 세 개는 무조건 있어야 하는 필수값이라, 없으면 페이지 생성 자체를 미루게 짰습니다. 특히 날짜는 절대 대충 기본값 넣지 않고 꼭 물어보게 했고, 목표(학습/기획/조사/구현/수정/테스트)도 대충 찍는 게 아니라 제안하고 확인받는 식으로 만들었습니다.

중요도·담당자는 처음엔 물어보되, 한 번 확인된 값은 같은 대화 안에서는 재사용하게 해서 매번 담당자 누구냐고 안 물어보게 했습니다.

### 2. 진행 중인 업무 업데이트

대화에서 나온 얘기를 세 갈래로 나눠서 각자 다른 곳에 기록하게 했습니다.

- 사소한 사실/블로커 → 업무 페이지 진행메모에 추가
- 상태 자체가 바뀐 거(보류, 진행중 등) → "막혔어" 같은 말만 들어도 알아서 진행상황 필드 바꾸고, 보류면 이유도 같이 기록
- 팀원이 봐야 하는 거 → 업무 로그 DB에 한 줄로 짧게 기록

### 3. 업무 과정

1. 결과·인사이트는 무조건 사용자한테 직접 받기
2. 산출물 있으면 공유 자료실 폴더에 만들고 업무 페이지에 링크
3. 진행상황 완료로 변경
4. 완료 체크박스 체크

### 4. 신규 프로젝트 설정

템플릿 복제해서 새 프로젝트 시작할 때, 프로젝트명·참여자 실명·초기 업무·마감일을 한 번에 물어보고, 개인 폴더는 빈 페이지로만 만들어두게 했습니다.

### 5. 개인 작업 일지

이건 나중에 추가한 건데, 대화하면서 그 사람이 뭘 했고 어떤 어려움을 어떻게 풀었는지 같은 게 쌓이면 그 사람 개인 폴더에 기록해주는 기능입니다.

근데 매 턴마다 쓰면 토큰도 아깝고 폴더도 지저분해지니까, 상태가 바뀌거나 업무가 완료되거나 대화가 마무리될 때 같은 자연스러운 시점에서만 몰아서 쓰게 했습니다. 사실 기반 내용은 확인 없이 바로 쓰게 설정했고, 오늘 배운 점 같은 그 사람 생각이 필요한 페이지는 대신 안 써주고 물어보게 했습니다.

### 6. 깃허브 자가 점검

이거 원래는 "다르면 자동 업데이트"로 짰다가 사고 한 번 크게 날 뻔했습니다. 레포가 오히려 구버전인데 그걸 기준으로 자동 덮어쓰기 했으면, 방금 만든 기능 자체가 삭제될 뻔했거든요.

![시무룩한 흰 고양이 밈](../../assets/study/claude-skills-intro/05-github-selfcheck.png)

그래서 지금은 절대 자동으로 덮어쓰지 않고, 레포랑 계정 저장본 내용을 통째로 비교해서 어느 쪽이 뭘 더 가지고 있는지 양쪽 다 보고만 하고, 사용자가 직접 판단하게 바꿨습니다. 매주 일요일에만 체크하고, 마지막 점검일도 기록해둬서 매번 새로 확인 안 하게 짰습니다.

이렇게 6개 워크플로우로 나눠서 만들었는데, 지금 보니까 이것도 그냥 정신없이 늘어난 거 같네요. 처음엔 4개였는데 만들다 보니 자꾸 필요한 게 생겨가지고...
